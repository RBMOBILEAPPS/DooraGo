## 2. Model Installation onto Connected Android Device

To avoid APK bloat and unnecessary duplication, the model is **not** bundled as a regular Flutter asset. Instead, use one of the following safe installation mechanisms:

### Method 1: Automatic Windows Script (Recommended)
Run from the project root:
```cmd
scripts\install_model.bat
```
*(Or specify custom path: `scripts\install_model.bat "path\to\mobile_actions_q8_ekv1024.litertlm"`)*

### Method 2: Manual ADB Commands
```bash
# Step 1: Push the model to Android staging directory
adb push "D:\DooraGo\mobile_actions_q8_ekv1024.litertlm" /data/local/tmp/mobile_actions_q8_ekv1024.litertlm

# Step 2: Install directly into the app's internal sandbox
adb shell "run-as com.rbapps.doorago mkdir -p files/models"
adb shell "run-as com.rbapps.doorago cp /data/local/tmp/mobile_actions_q8_ekv1024.litertlm files/models/mobile_actions_q8_ekv1024.litertlm"

# Step 3: Remove temporary staging copy
adb shell "rm /data/local/tmp/mobile_actions_q8_ekv1024.litertlm"
```

*Note:* On devices where `run-as` is restricted, DooraGo will automatically detect the staged model file at `/data/local/tmp/mobile_actions_q8_ekv1024.litertlm` on app launch, securely copy it into `context.filesDir/models/` via an atomic temporary file, and use it directly.

## 3. App Model Resolution & Verification Rules

1. **Existence Check**: Checks `context.filesDir/models/mobile_actions_q8_ekv1024.litertlm`.
2. **Persistence Guarantee**: If the file exists and is non-empty, DooraGo **does NOT copy it again on every launch**.
3. **Verification**: Checks filename and verified size (`288,964,608 bytes`).
4. **Missing Model Handling**: If the model is not found, the app transitions to `ERROR` status and surfaces the code `MODEL_NOT_FOUND` along with actionable ADB installation instructions.
5. **No Cloud Fallback**: DooraGo never downloads the model over the internet and never calls cloud APIs.

## 4. Testing Inference with the Real Model

### Prompt:
> `"Turn on the flashlight"`

### Expected Engine Behavior:
- The app transitions to `PROCESSING` status while on-device inference runs.
- Inference executes locally via `com.google.ai.edge.litertlm.Engine` with `Backend.CPU()`.
- The native engine collects tokens via `conversation.sendMessageAsync(prompt).collect`.
- The generated response is returned directly to Flutter.
- The app **does NOT** actually turn on the hardware flashlight at this stage. It inspects and presents the raw function call / tool invocation generated by the MobileActions model (e.g., `call:turn_on_flashlight()` or similar tool call schema).
- The UI transitions back to `READY` upon completion.
